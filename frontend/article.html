Running a Software Project With an AI Agent: PRD to Prod

The sprint pattern I use to hand real software work off to an LLM — phase 0 discovery, planning docs, phase reports, and AGENTS.md.

AT Atha Tharizky Jul 7, 2026 8 min read 1,204 views

The first time I tried to hand a real feature to an LLM, it went sideways in about fifteen minutes. The agent invented an import that didn't exist, "fixed" a test by deleting it, and confidently declared the task done. Classic. The problem wasn't the model — it was that I'd given it a vague paragraph and hoped for the best.

After a year of running projects this way, I've landed on a pattern that actually works. It's not fancy, and most of it is just writing things down. But the shape of the writing matters.

The shape: phases, not prompts

The single biggest shift is thinking in phases, not prompts. Each phase has a goal, a set of tasks with difficulties and dependencies, and a report at the end. The agent never moves to the next phase until the current one is verified working. 

PRD / Idea
    │
    ▼
Phase 0 — Discovery & Exploration
Phase 1 — Foundation
Phase 2 — Core feature
Phase 3 — Integration
...
    │
    ▼
Retro / Ideas

The four files that make delegation work

Inside each docs/sprint-N/ folder I keep four documents. These are the things that turn a flailing agent into a reliable contributor.

1. tasks.md — the source of truth

Every task has an ID, a difficulty (Easy / Medium / Hard), dependencies, and a status emoji: ⬜ pending, 🔵 in_progress, ✅ completed, ❌ blocked. Only one task is in progress at a time. Nothing gets marked done until it's tested.

If a task can't be marked ✅, it isn't done. "It compiles" is not done. Run it, look at the output, then mark it done.

2. architecture.md — the WHY

Tech stack decisions with a decision matrix and — more importantly — a "rejected alternatives" table. Future-you (and future-agent) will thank you for explaining why you didn't pick the obvious thing.

3. data-design.md — the shapes

Show the data at every pipeline stage. Real schemas, not prose. Note the quirks: duplicate keys, mixed casing, the field that's suddenly null for no reason. These are where agents trip hardest.

4. AGENTS.md — the handoff

This is the file you point another LLM at. It lists what already exists (do NOT rebuild), the exact file structure to create, a numbered implementation checklist, and "done criteria" so the agent can self-validate.

The communication loop

  • Ask before committing — "Confirm and I'll commit."
  • Test immediately after building. Run the code. Show the output.
  • Update docs after every phase — report + tasks.md update.
  • Document findings, not just results. What surprised you? What failed?

What this buys you

On my last project this workflow produced five services across three languages, ~2,500 lines of documentation, and a working RAG pipeline — in a sprint I could actually follow. More importantly, when I came back two weeks later, I could pick up exactly where I left off because every decision was written down.

The agents didn't get smarter. I just got more disciplined about what I told them.
